# Limb-itless — Backend history

This repository is a fresh, private copy of the Limb-itless backend. The
original branch-per-task history is not carried over; this file is the
record of what was built, in order, so the progression is still legible.

The backend is **FastAPI + SQLAlchemy 2.0 + Alembic (Postgres) +
Pydantic v2**. Every clinical entity is practice-scoped for tenant
isolation, role-gated at the API layer, and audited on every read and
write. Tasks were shipped as small stacked slices, each with its own
tests and (where it added data) matching seed fixtures.

Conventions that hold throughout:

- **Scoping** via `PracticeScoped` / `SiteScoped` mixins + a
  `get_request_scope` dependency — isolation is structural, not per
  endpoint.
- **RBAC** via `require_roles(...)`; other-practice reads return `404`,
  never an existence leak.
- **Audit** via `AuditRecorder` / `get_audit_recorder`, committed inside
  the request transaction.
- **crud.py** is the single DB-access layer.
- **PG enum migration pattern** (used cleanly many times): pre-create the
  type with `sa.Enum(...).create(bind, checkfirst=True)`, then use a
  *separate* `postgresql.ENUM(*values, name=..., create_type=False)` for
  the column inside `op.create_table` — reusing one object re-issues
  `CREATE TYPE` and fails `DuplicateObject`.

## Phase 0 — Foundations

### R-01 — Project scaffold
Initial FastAPI application (`app/main.py`), README with run
instructions, `requirements.txt`.

### R-02 — Dependency shape
Switched to `fastapi[standard]` (bundles uvicorn, httpx, etc.) rather
than `fastapi` + a separate `uvicorn`.

### R-03 — Alembic + Postgres
Removed the placeholder `Item` model/schema/crud trio. Added Alembic
(`env.py` reads the URL + metadata from `app.database` / `app.models`;
empty baseline revision). Added `alembic` + `psycopg[binary]`. Switched
the `DATABASE_URL` default from SQLite to local Postgres. Added
`.env.example`.

### R-04 — Practice + Site models
`Practice` and `Site` models with native PG enums (`practice_type` /
`site_type`), a `TimestampMixin`, and `PracticeScoped` / `SiteScoped` FK
mixins. Autogenerated migration. `app/scoping.py` (`scope_to_practice` /
`scope_to_site` / `apply_scope` + a `RequestScope` dataclass). No
endpoints yet — those need the authenticated caller from R-05.

### R-05 — JWT auth + RBAC
`User` model + migration (`user_role` enum, nullable practice/site FKs).
`app/config.py` (JWT env vars), `app/security.py` (bcrypt + PyJWT:
access token with role/practice_id/site_id claims, refresh token,
`decode_token` with a type check), `app/deps.py` (`get_current_user`,
`require_roles`, `get_request_scope`), `app/routers/auth.py`
(`POST /auth/login` OAuth2 form, `POST /auth/refresh`, `GET /auth/me`).
Stateless refresh (no revocation table — noted as later hardening).

### R-06 — Audit log
`AuditLogEntry` model (actor_id, action enum, entity_type, entity_id,
timestamp, plus practice_id for practice-scoped audit queries; actor and
practice FKs `ON DELETE SET NULL`) + migration. `app/audit.py`:
`record()` append helper (flush, no commit), `AuditRecorder` dataclass,
`get_audit_recorder` dependency. Deliberately explicit calls rather than
middleware so each entry carries the real action and entity id.

### R-07 — Dev seed script
`scripts/seed.py` (`python -m scripts.seed`, `--reset`): 2 practices
(a multi-site hospital network, a single-site private practice), one
user per role, shared dev password. Idempotent get-or-create.

### R-08 — CI workflow
`.github/workflows/ci.yml`: a `tests` job (pytest) and a `migrations`
job (alembic upgrade / check / downgrade / upgrade against a Postgres
service container).

### R-09 — CORS
`CORSMiddleware` (Starlette, no new dep) with an allowlist from
`CORS_ALLOW_ORIGINS` (default: the local Angular dev origin, both host
spellings).

### R-10 — Names on `/auth/me`
`/auth/me` `UserRead` gains `practice_name` / `site_name`, resolved from
the user's relationships in the endpoint. No schema change.

## Booking (requirements §5.9 – §5.10)

Model: publishing an availability slot **is** the confirmation — no
separate approval step. Reschedule is one atomic linked action with its
own status.

### R-35 — Availability + medical aid
`MedicalAidMembership` model/schema/crud. `AvailabilitySlot` CRUD +
practitioner publish/block endpoints + `GET /portal/availability`.
Migration.

### R-36 — Appointments
`Appointment` entity covering the lifecycle: book a slot,
cancel (patient — notice-window flagged), cancel (practitioner — reason
required), no-show. `Practice.cancellation_notice_hours` (default 24).
Migration.

### R-37 — Reschedule as one atomic action
`AppointmentStatus.rescheduled` + `rescheduled_to_id` /
`rescheduled_from_id` self-FK ints (no relationship object).
`POST /appointments/{id}/reschedule` (staff) +
`POST /portal/appointments/{id}/reschedule` (patient), both return

reschedule into a different practitioner's slot. Migration.

### R-38 — Coverage determination
`CoverageDetermination` (one row per appointment; opens `pending`
automatically when a medical-aid patient books, self-pay gets none).
Reviewer `GET/approve/deny /review/coverage[/{id}]`; staff
`GET /appointments/{id}/coverage`. Reschedule carry-over: an approved,
unexpired, same-type determination moves with the visit, otherwise a
fresh `pending` one opens. **Reconciled R-34**: `User.scheme_name`
matched against a patient's active membership is now an automatic,
cross-practice access path that *coexists* with the manual `ReviewGrant`
(`crud._reviewer_access_clause` = OR of both). Migration.

### R-39 — Per-patient progress report
`GET /patients/{id}/report` (same reader roles as the timeline).

### R-40 — Self-registration + walk-in-record claim
`POST /auth/register` (email + password ≥ 8 chars → always a

`POST /account-link-requests` (patient role only): identity number +

`Patient(...)` constructor. Scope decision, flagged: the "walk-in at more
than one practice" case was left for a later slice (later closed by
R-46).

## §5.6 Communication / Notifications

In-app only for the first pass (email is R-43). No background scheduler —
time-based kinds use a `deliver_at` column + a cron-driven maintenance
pass.

### R-41 — Notifications core + event triggers
`Notification` model (`user_id`, `type`, `payload` JSON, `deliver_at`,
`read_at`, `created_at`) + `NotificationType` enum. Migration.
`app/notifications.py`: `notify()` append helper (flush-only, no-op
without a recipient, **never raises into the caller's request** — a
failed notification must not fail the booking/PROM it rides with;
logged) + one `notify_*` per event. `app/routers/notifications.py`:
`GET /notifications` (mine, `?unread`, paged, hides future `deliver_at`),
`/unread-count`, `POST /{id}/read`, `/read-all` — no role gate, no
practice scope, reads not audited. Triggers wired into the existing
routers: `appointment_booked` / `_cancelled` / `_rescheduled`,
`coverage_decided` (→ patient), `prom_flagged` (→ current care team),
`patient_reassigned` (→ the assigned clinician). Seed: a starting inbox
for two users.

### R-42 — Appointment reminders + subject pointer
`Notification` gains `subject_type` / `subject_id` (a logical pointer
like `audit_log_entries` — lets a superseded reminder be found and
deleted without a JSON query, and lets the frontend deep-link a row);
backfilled onto every R-41 helper. Migration.
`notify_appointment_reminder` writes at booking time with
`deliver_at = scheduled_start − 24h`; `supersede_appointment_reminders`
deletes a still-pending reminder on cancel / no-show / reschedule (an
already-due one is left alone). Wired staff + portal.

### R-43 — Email delivery
`app/email.py` — `send()` with three backends via `EMAIL_BACKEND`:
`noop` (default), `console` (logged), `smtp` (stdlib `smtplib` +
STARTTLS, no new dependency). `notifications.render_email()` mirrors the
frontend's summary text. `Notification.emailed_at` column (migration) —
NULL until sent; a failed send stays NULL so the next pass retries it
(the "retry, don't silently drop" requirement).
`crud.dispatch_due_emails()` = one idempotent pass over due, recent
(within `EMAIL_DISPATCH_MAX_AGE_DAYS`, default 7), not-yet-emailed rows.
`POST /notifications/dispatch-due` — token-gated via an
`X-Dispatch-Token` header (`503` if `NOTIFICATIONS_DISPATCH_TOKEN` is
unset, `401` on mismatch); meant for a cron. Tradeoff, flagged:
immediate-kind emails go out on the next dispatch tick, not the instant
of the event — the in-app notification is still immediate.

### R-44 — Milestone due / overdue notifications
New `NotificationType` values (`ALTER TYPE … ADD VALUE` migration). Done
via the R-43 maintenance pass, **not** pre-created at pathway-apply time
(that would fan out 7 milestones × 2 kinds × every care-team member per
call). `crud.scan_milestone_notifications(grace_days)` — open milestones
past `target_date` get a `milestone_due` per care-team member; past
`MILESTONE_OVERDUE_GRACE_DAYS` (default 7) also a `milestone_overdue`.
Idempotent per (milestone, kind) via
`subject_type='recovery_milestone'`. Completing a milestone supersedes
its unread nudges. The dispatch endpoint now runs the milestone scan
first, then the email pass; its response became
`NotificationMaintenanceResult`. `notifications.care_team_user_ids()`
factored out of `notify_prom_flagged`.

## Multi-practice walk-in claim

### R-46 — `Patient.user_id` → a join table
The portal link was 1:1 (`Patient.user_id`, unique). It moves to
**`account_patient_links`** (`patient_id` unique, `user_id` not), so one
login can hold a record at each practice. Migration: create the table,
backfill from `patients.user_id`, **drop the column** (+ its FK / index).
`Patient.user_id` survives as a **read-only Python property** off the
link, so the notification / appointment code that reads
`appointment.patient.user_id` is untouched. `crud`:
`get_patient_for_user` → `list_linked_patients` / `get_linked_patient` /
`patient_link_owner` / `link_patient` / `unlink_patient`.
`claim_walk_in_patient` writes a link row. Portal: a `get_my_patient`
dependency reads a `?patient_id=` query param — optional and
auto-resolved when the login has exactly one record (**full
back-compat**), required (`400`) for a multi-record login, `404` for a
record the login isn't linked to. New `GET /portal/records`. The
"already linked to a record" `409` on `POST /account-link-requests` is
removed (claiming another is the point); staff `link-user` `409`s only
when the record is on a *different* login. Seed: a second record for the
main portal login at another practice.

## Body-map v2 — posterior view

### R-47 — `Device.map_face`
`map_x` / `map_y` only made sense on one (front) figure. A new
`MapFace` enum column (`anterior` / `posterior`) says which face those
fractions belong to, so a spinal / posterior device can be placed on a
back view. Migration `b8d2f1c4a933` (pre-create the PG enum, then a
`create_type=False` handle for `add_column`). Nullable, and kept
consistent with the position by `crud._apply_map_face_rule`, called
from `create_device` / `update_device`: a position set without a face
defaults to `anterior`, and clearing the position (`map_x` / `map_y`
→ NULL) forces `map_face` back to NULL. So `PATCH {"map_face":
"posterior"}` alone flips a placed device without moving it, and a face
sent for an unplaced device is simply dropped. Flows through the
existing device POST / PATCH and the `/patients/{id}/devices` overview —
no new endpoint. Seed: Refilwe's TLSO moves to the posterior face (her
AFO stays anterior, so the front/back toggle has one marker on each).
369 BE tests (5 new), `alembic check` clean, migration round-trips.

## Session revocation

### R-48 — "sign out everywhere"
Refresh (and access) tokens were stateless with no way to invalidate a
lost or leaked one — flagged since R-05. Added `User.token_version`
(`Integer`, `default 0` / `server_default '0'`; migration
`c4f7a9e2b610`). Every access and refresh token now carries a `tv`
claim = the user's `token_version` at issue time
(`security.create_access_token` / `create_refresh_token` gained a
`token_version=` kwarg, threaded through `auth._tokens_for`).
`deps.get_current_user` and the `/auth/refresh` handler reject a token
whose `tv` no longer matches the user's current value. New
`POST /auth/logout-all` (any authenticated user) bumps
`user.token_version`, so every token issued so far — the one that made
the call included — stops validating and the client must log in again.
New `schemas.MessageResponse {detail}`. 373 BE tests (4 new in
`test_auth.py` "session revocation" block), `alembic check` clean,
migration round-trips, API live-smoked (fresh token works → logout-all →
same token 401 + its refresh token 401 → a new login works).
